## Архитектурное решение: три слоя рендера

Вопрос «iframe или `<astroway-horoscope-card>`» поставлен неверно, это три независимых слоя:

1. **Транспорт**: кто ходит в API, браузер посетителя или PHP нашего сервера.
2. **Место рендера**: отдельный документ в iframe или разметка в DOM страницы.
3. **Слой интерактива**: ничего, custom element, полноценный JS-виджет.

Индексацию, наследование темы, доступность и вёрстку решает **слой 2**. Custom element сам по себе
не решает ничего: если данные тянутся фетчем, для краулера это та же пустота, что и iframe.
Клиентский фетч у нас вдобавок закрыт CORS-whitelist'ом.

Как это сделано у конкурента: PHP кладёт `<roxy-horoscope-card>`, внутрь него fallback-разметку
**и** `<script type="application/json">` с полными данными, компонент апгрейдит уже готовый HTML.
Цена `roxy-ui.js` 439 КБ, лениво подключается только на страницах с виджетом.

**Принятое решение:** копируем слоистость, не копируем цену.

- Слой 2 переезжает на server-side PHP-рендер. Это и есть содержание 1.0.0.
- Тег `<astroway-horoscope-card>` вводится **сразу**, как обёртка серверной разметки, без единой строки JS.
  Разметка внутри работает сама. Имя тега дёшево ввести сейчас и дорого вводить потом:
  апгрейд до интерактива не потребует ни менять шаблоны, ни ломать CSS пользователей второй раз.
- Слой 3 добавляется точечно и позже, только где интерактив нужен: ховер по планетам на колесе,
  аккордеоны интерпретаций, вкладки. У нас сейчас фронтового JS для виджетов ноль байт,
  начинать с чистого листа дешевле, чем тащить чужой бандл.
- iframe не выбрасывается, а понижается до явного запасного режима там, где server-side пока невозможен.

Ломающее изменение разметки делается **один раз и сейчас**: при <10 активных установках
цена почти нулевая, через полгода она станет реальной. Semver при смене разметки требует мажора.

## Установленные факты об API (проверены curl 2026-07-28)

- `/v1/embed/*` анонимно отдаёт HTML, лимит 30/час по IP, на всех путях `x-robots-tag: noindex, nofollow`.
- `/v1/public/horoscope/daily`, `/v1/public/moon-phase`, `/v1/public/tarot/daily` анонимно отдают JSON, тот же лимит 30/час по IP.
- `POST /v1/public/chart` **анонимно отдаёт полную натальную карту** (HTTP 200, 33.7 КБ: planets, houses, aspects, antiscia). GET-пути `/v1/public/natal`, `/bodygraph`, `/human-design` отдают 401, но это не значит, что анонимного натала нет. Контракт полей надо выяснить до реализации: тестовый POST с `lat`/`lng`/`tz` вернул карту для координат 0,0, то есть переданные значения были проигнорированы.
- Анонимного источника нет только для бодиграфа и Human Design.
- В `/v1/public/*` есть также `horoscope/weekly`, `horoscope/monthly`, `planet-of-day`.
- Роута `today-in-sky` в api **не существует вовсе** (в `embed.ts` 15 роутов, этого среди них нет). Живой 401 это провал сквозь embed-роутер в общий auth-wall, а не эндпоинт за ключом.
- Без параметра `lang` контент приходит на украинском.
- CORS на `/v1/public/*` работает **по whitelist**: произвольный домен не получает `access-control-allow-origin`. Браузерный fetch с сайта пользователя будет заблокирован.
- Заголовок `X-AstroWay-Site-URL` разрешён в `access-control-allow-headers`, но на учёт лимита не влияет: счётчик уменьшается по IP независимо от него. Учёта по домену на API нет.
- **Ключ не спасает от анонимного лимита на публичных путях.** `publicRateLimitMiddleware` смонтирован на `/api/v1/public` (index.ts:117) и `/api/v1/embed` (index.ts:135), то есть до `app.use('/api/v1', authMiddleware)` (index.ts:174), и считает `req.ip` без всякой проверки ключа. Бакеты `user:`/`key:` работают только на authed-роутах, смонтированных после auth. Server-side вызов на `/v1/public/*` даже с ключом тикает IP-счётчик сервера.
- **Ключ физически не попадает в iframe**: `PublicClient::embed_url()` собирает URL только из whitelisted-параметров виджета. Поэтому у платящих установок iframe жжёт анонимную квоту посетителя.

## Почему у нас iframe (контекст)

Коммит v0.1.0 (2026-05-12): анонимный тариф считается по IP посетителя, поэтому MVP переложил вызов
на браузер через iframe, и только так работает обещание «no account, no key». README плагина
с самого начала описывал гибрид с client-side fetch из `/v1/public/*`, но гибрид не был реализован:
все 6 шорткодов безусловно зовут `embed_iframe()`. Как выяснилось при ревью, client-side fetch
и не мог работать: CORS на `/v1/public/*` закрыт whitelist'ом.

## Фаза 2. Форма для посетителя

Ограничение, которое надо назвать явно: форма предполагает установку **с API-ключом**. Для установок
без ключа каждый посетитель тратит общую анонимную квоту сайта, поэтому там форма либо недоступна,
либо жёстко ограничена.

Независимость от 3.2 достигается **только** если форма ходит на authed-роуты (`POST /v1/chart`
с заголовком `X-Api-Key`), которые смонтированы после `authMiddleware` и считаются в бакете
`user:`/`key:`. Если реализовать её через `/v1/public/*`, даже с ключом, сайт упрётся в 30/час
на IP сервера. Это обязательное требование к реализации, а не деталь.

- [ ] 2.1 Форма для натальной карты и бодиграфа: дата, время, поиск города. Внимание:
      `astroway_atlas_search` зарегистрирован только как `wp_ajax_` (`class-admin.php:25`),
      `wp_ajax_nopriv_` нет ни в одной сборке, поэтому незалогиненному посетителю поиск города
      сейчас недоступен. Нужна отдельная публичная точка со своим лимитом: наивный `nopriv`
